## Plan: Account Timezone Support

Add timezone as a Better Auth user field and keep the auth-owned user row as the single source of truth. Capture the browser timezone during signup, expose manual editing on a new /settings/account page, and mount one reusable mismatch banner in the app shell that compares the stored account timezone with the current device timezone. Cache dismissal only on the current device, keyed by user and dismissed device timezone, so it resets automatically when that device timezone changes.

**Steps**
1. Phase 1 — Data model and auth wiring. Add a timezone additional field to the Better Auth user model in /Users/callumgare/repos/edgeucator/src/lib/server/auth.ts rather than hand-editing the generated schema, then regenerate /Users/callumgare/repos/edgeucator/src/lib/server/db/schema/auth.ts with npm run auth:schema. Follow that with a Drizzle migration for the new user.timezone column and review the generated SQL before it is committed. Make the field required in the final schema, and in the migration backfill any existing rows that have no timezone to `UTC` before enforcing the non-null constraint.
2. Add a shared timezone validation and normalization helper that both signup and account updates use. The helper should accept plausible IANA timezone identifiers, reject garbage cleanly, and preserve a canonical string for storage so the signup flow, account form, and banner update path cannot drift.
3. Phase 2 — Signup capture. Extend /Users/callumgare/repos/edgeucator/src/lib/schemas/signupForm.ts and /Users/callumgare/repos/edgeucator/src/lib/components/SignupForm.svelte with a hidden timezone field populated from Intl.DateTimeFormat().resolvedOptions().timeZone at submit time. Pass that timezone straight through locals.auth.api.signUpEmail in /Users/callumgare/repos/edgeucator/src/routes/(public)/signup/+page.server.ts so the first device timezone is written as part of user creation instead of via a second follow-up write.
4. Phase 3 — Settings/account integration. Reuse the existing /Users/callumgare/repos/edgeucator/src/routes/(auth-required)/(app)/settings/account/+page.server.ts and /Users/callumgare/repos/edgeucator/src/routes/(auth-required)/(app)/settings/account/+page.svelte route as the long-term home for user-scoped account settings, and extend the current account form rather than creating a parallel page. The settings hub at /Users/callumgare/repos/edgeucator/src/routes/(auth-required)/(app)/settings/+page.svelte already links there, so this feature should fit the current information architecture rather than changing it again.
5. Build on the existing account page with the established superforms pattern. Extend /Users/callumgare/repos/edgeucator/src/lib/schemas/accountForm.ts to include timezone alongside name, load the current timezone into the existing form in /Users/callumgare/repos/edgeucator/src/routes/(auth-required)/(app)/settings/account/+page.server.ts, and persist name/timezone changes through locals.auth.api.updateUser rather than the current direct Drizzle update. Because locals.user is populated from Better Auth session state and cookie cache, using the auth API is the safer way to keep the stored row and future session reads aligned. Reuse InputField patterns where they fit, but prefer a timezone-specific control or helper over forcing 400+ values through a generic text field without guidance.
6. Give the account page a simple “use this device timezone” affordance in addition to manual editing. The page should expose the current device timezone client-side so one click can copy it into the form without making the stored account timezone permanently follow the browser automatically.
7. Phase 4 — Cross-page mismatch banner. Add a reusable TimezoneWarning.svelte under /Users/callumgare/repos/edgeucator/src/lib/components and mount it in /Users/callumgare/repos/edgeucator/src/routes/(auth-required)/(app)/+layout.svelte beside EncryptionGate.svelte. That keeps the banner available on home, partners, and settings without duplicating page-level markup.
8. Feed the banner from layout data by extending /Users/callumgare/repos/edgeucator/src/routes/+layout.server.ts to whitelist user.timezone along with the existing id, name, email, and image fields. The banner should compute device timezone client-side, suppress itself when the stored timezone already matches, and otherwise offer Update timezone and Dismiss actions.
9. Keep dismissal device-local only. Store the last dismissed device timezone in localStorage under a key namespaced by the signed-in user id, and treat that dismissal as valid only while the current device timezone is unchanged. As soon as the device reports a different timezone, the stored dismissal no longer applies and the banner becomes eligible again. This satisfies the per-device requirement without adding server state that would incorrectly affect other devices.
10. Add a shared server-side persistence path for banner-triggered updates so the account page and the banner do not duplicate timezone write logic. Recommended shape: extract a small timezone update helper and call it from both the account page action and a dedicated authenticated endpoint or named page action under /settings/account.
11. Phase 5 — Tests and documentation. Add server tests for signup persistence and account-page updates, component coverage for the banner visibility and dismissal rules, and end-to-end coverage that exercises mismatch, dismiss, timezone change, and account-page save flows. Update any now-stale auth or settings comments, and if the finished implementation spans enough files to need durable explanation, add a feature doc and copy the final implementation plan to docs/historical-plans per repo convention.

**Decisions**
- Store timezone on the Better Auth user row, not in a separate app-owned preferences table, because this is a core account attribute and Better Auth already supports user additional fields plus updateUser and signUpEmail typing for them.
- Make timezone a required persisted field. Existing rows are backfilled to `UTC` in the migration before the non-null constraint is enforced, and new signups should always supply a validated timezone.
- Use the existing /settings/account page as the timezone editing surface. The current settings root already acts as the hub and links to account, security, partners, and conditional encrypted-message settings, so this feature should extend that structure in place.
- Keep banner dismissal in localStorage on the current device only. Do not persist dismissal server-side, because that would violate the requirement that dismissing on one device must not hide the banner on another.
- Reuse one shared timezone write helper behind both the account page and the banner update path so validation and persistence stay identical.
- Treat testing as part of the feature definition: every requirement should have at least one executable automated check, with migration/backfill covered directly rather than only by inference from post-migration app behaviour.

**Further Considerations**
1. Account-page dependency: if another branch lands /settings/account first, merge the timezone form into that route instead of creating a parallel scaffold, but keep the rest of the plan unchanged.
2. Timezone control UX: recommend either a validated text input with a one-click “use this device timezone” action or a deliberately searchable chooser. A long static select is likely too clumsy for this app unless the new account page is already adopting a richer picker.
3. Existing users backfilled to `UTC` will immediately be eligible for the mismatch banner on non-UTC devices. That is consistent with the new requirement, but the implementation should keep the copy concise so the first post-migration prompt feels corrective rather than alarming.
