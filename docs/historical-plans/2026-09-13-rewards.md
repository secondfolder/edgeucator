## Plan: Rewards Feature

Add a dedicated rewards domain with separate self-reward and partnership-reward storage, then surface it in two places: a new partner rewards subroute for full partner-specific management/claiming, and a new home-page rewards section that combines self rewards with claimable partner rewards. The recommended shape is explicit rather than polymorphic: keep self and partnership rewards in separate tables and service functions so the permission model stays readable, the queries stay cheap on D1, and the shared-control authorship rule does not disappear into nullable scope columns.

**Steps**
1. Phase 1: Model the reward domain and persistence layer.
   Add a new pure reward-domain module alongside the existing partnership domain that defines the shared rules the UI and server must agree on: self rewards are always self-manageable and self-claimable; partnership reward management follows `partnership.canEdit`; partnership reward claiming follows authorship and credit balance, not control alone, so a user can never claim a partnership reward whose `createdByUserId` is their own. Preserve the current partnership mapping rule by always deriving viewer-facing partner data from `viewPartnership()`.
2. Phase 1: Extend the Drizzle schema in the existing app schema file with six reward tables.
   Use separate tables for `self_rewards`, `self_reward_credits`, `self_reward_claims`, `partnership_rewards`, `partnership_reward_credits`, and `partnership_reward_claims`. Each row should use the repo’s standard UUID text ids and shared `timestamps` helper. Credits should be stored as absolute non-negative integer balances, with one unique row per user for self credits and one unique row per `(partnership_id, user_id)` for partnership credits. Partnership rewards should store `createdByUserId`; both claim tables should snapshot at least the reward title and credit cost at claim time so visible history does not rewrite when a reward is later edited. Use `active` instead of hard delete so claim history remains coherent and rewards can be hidden without removing old claims.
3. Phase 1: Generate and review the migration, then extend the test fixtures.
   Run the normal schema generation flow, inspect the generated SQL for foreign keys, indexes, default values, and unique constraints, and add reward fixture helpers beside the existing partner and messaging helpers so tests can create self rewards, partnership rewards, balances, and claim history through real server paths rather than raw inserts where possible.
4. Phase 2: Add validation schemas and server-side reward services.
   Introduce Zod schemas for reward create/edit, balance updates, and reward claims. Mirror the existing forms pattern: typed schema in `src/lib/schemas`, validate in the route load/actions, and keep error messages actionable. Then add a new server module parallel to messaging/partnerships that owns all reward queries and mutations. It should expose a membership gate built on `getPartnershipForUser()`, explicit column lists for every query, separate self and partnership read models, manager-only mutations for create/edit and credit-setting, and atomic claim operations using `db.batch()` to insert a claim record and deduct credits together.
5. Phase 2: Define the home and partner view models before touching route code.
   Add shared view types in the cross-boundary types file for reward rows, credit summaries, claim-history entries, and home-page sections. The partner-page model should carry both capability axes separately: `canManageRewards` and per-row `canClaim`. The home-page model should carry one self section plus zero or more partner sections, where a partner section appears only when the viewer has active counterpart-authored rewards in that partnership to claim.
6. Phase 3: Add the partner rewards route and hook it off the existing partner page.
   Update the partner landing page to include a new Rewards button next to Messages. Add a new `partner/[id]/rewards` server route and page that reuses the accepted-partnership gate already used by messages. The load should fetch the partnership view, partnership rewards, the viewer’s current credit balance, the counterpart’s balance when the viewer is allowed to set it, and recent claim history. The page should render one list of rewards with inline edit controls for managers, add-new-reward controls for managers, active/inactive toggles, and claim actions that appear only on active rewards created by the other partner and only when the viewer has enough credits. Under shared control, both members can create and edit any reward, but each reward still remains non-claimable by its author.
7. Phase 3: Keep the partner route rules explicit when control changes.
   Do not derive claimability from current control alone. Existing partnership rewards should retain their author and remain non-claimable by that author even if control later flips. Management rights may expand or shrink with control changes; authorship-based claimability should not silently change. This needs to be encoded in the service layer and covered by tests so future control edits do not create a privilege bug.
8. Phase 4: Extend the home page into a rewards hub.
   Add a rewards load step to the existing home page server load, using the current `parent()` partner list pattern rather than re-querying partnerships. The new home rewards service should return: the user’s self rewards with self credit balance and recent self-claim history; then one section per partner containing only active rewards authored by that partner which the viewer may claim. Reuse the same reward row componentry where possible so claim affordances behave identically on home and on the partner rewards page. Keep the home page’s partner sections claim-focused; do not duplicate partner reward management there.
9. Phase 4: Implement the self rewards section on home as the self-managed scope.
   The self section should be the only place in the first pass where a user manages their own rewards: add/edit self rewards, toggle active/inactive, set their own self credit balance, view visible self claim history, and claim their own active rewards when their self balance covers the cost. This satisfies the requested “set for and claim for yourself” behavior without introducing a second self-rewards route.
10. Phase 5: Add coverage at every existing test layer.
    Add pure tests for the reward-domain permission rules, especially the shared-control case where both users can manage but neither may claim a reward they authored. Add server tests for membership gating, 404 behavior for strangers and pending invites, manager-only credit-setting, inactive reward visibility, claim batching, insufficient-credit rejection, and author-blocked claims. Add route tests for the new partner rewards load/actions and the home-page rewards aggregation. Add an end-to-end rewards spec covering: sole-control partner flow, shared-control partner flow, self rewards on home, home-page collation of partner sections, inactive rewards disappearing from claim lists, and visible claim history updating after a claim.
11. Phase 5: Update feature documentation as part of the same change.
    Create `docs/rewards.md` describing the data model, the separation between self and partnership rewards, the credit-balance rules, the shared-control authorship restriction, and the home-page aggregation behavior. Update `docs/partners.md` where partner screens and control-gated actions are described so rewards becomes part of the documented partner feature surface. Update the feature-doc table in `AGENTS.md` to list the new rewards doc.
12. Phase 5: Run the full verification loop after the focused reward tests pass.
    Verify the new targeted tests first, then run the repo’s required finish-line commands: `npm run check`, `npm run lint`, `npm test`, and `npm run test:e2e`. If the home-page rewards UI introduces additional Web Awesome buttons with `onclick`, remember the existing a11y-ignore comment convention from `AGENTS.md` so the checks remain honest.

**Decisions**
- Use separate self-reward and partnership-reward tables instead of one polymorphic reward table.
- Use active/inactive state instead of hard delete in the first version so visible claim history stays stable.
- Treat partnership reward claimability as author-based: a user may not claim a partnership reward they created, even under shared control.
- Treat credits as absolute non-negative balances that managers set directly rather than as adjustment-only deltas.
- Keep partner reward management on the partner rewards page; keep home partner sections claim-focused; keep self reward management on home.
- Preserve reward authorship across later control changes so claim restrictions do not silently mutate when control flips.

**Further Considerations**
1. If the home page becomes too tall once self rewards, partner rewards, and unread links coexist, collapse each rewards section with a default-open summary rather than moving management off home; that preserves the requested collation without creating a second self-rewards destination.
2. If claim history grows noisy, show a recent slice on home and the fuller history on the partner rewards page while still storing the full claim table from the start.
