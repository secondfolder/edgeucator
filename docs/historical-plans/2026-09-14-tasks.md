## Plan: Tasks Feature

Before adding the new user-managed tasks feature, first rename the existing guide-task concept everywhere to `edge task` so the codebase, schema, UI, docs, and tests no longer use the overloaded word `task` for two unrelated features. After that terminology split, add the new self and partnership tasks domain, reusing the rewards feature’s navigation and credit balances, and build task scheduling around a user-relative timezone model: every partner-task date or datetime stores which user it is relative to, defaults to the other partner on create, and renders timezone notes whenever the viewer is looking at a time anchored to someone else’s timezone.

**Steps**
1. Phase 0: Rename the existing guide-task concept to `edge task` across code, schema, and docs.
   Treat this as a prerequisite refactor, not a side cleanup. The current guide/task feature is concentrated in the `tasks` table in `src/lib/server/db/schema/app.ts`, guide UI, seed data, shared types, and repo documentation. Rename the concept consistently to `edge task` in human-facing copy, comments, types, symbols, tests, and database identifiers so the later user-managed tasks feature can use plain `task` without ambiguity. This includes the live Drizzle schema name, the SQL table name, relation names, type names like `TaskInstructions`, and any list/component props that still mean “guide step”.
2. Phase 0: Implement the database rename as a proper forward migration rather than rewriting history.
   Do not edit committed historical migrations by hand. Instead, add a new migration that renames the existing `tasks` table and its supporting index to something explicit like `edge_tasks` and `edge_tasks_guide_id_order_idx`, preserving all existing guide content. Update the Drizzle schema and snapshots to match. Because the repo already has committed `drizzle/0000_init.sql` through `0006_message-tags.sql`, the rename must land as a new migration that upgrades existing databases cleanly rather than pretending the old name never existed.
3. Phase 0: Rename the guide feature’s TypeScript surface so new tasks can use unqualified task language.
   Update the existing guide-task abstractions to names such as `EdgeTaskInstructions`, `EdgeTask`, `NewEdgeTask`, `EdgeTaskView`, and corresponding relation or component names where useful. Review the current guide pages and components so props like `tasks` that still mean “steps in a guide” become `edgeTasks` or similarly explicit names. Keep route URLs under `/home/guides/...` unless there is a separate product decision to change the user-facing guide terminology; this rename is about the internal concept and adjacent copy, not changing the guides feature IA.
4. Phase 0: Update the current guide UI and copy where `task` is ambiguous.
   Review user-facing strings like “This guide has no tasks yet” and the adult-content seed prose/comments that reference guide tasks. Rename these to `edge task` only where it actually helps disambiguate from the new feature; keep the copy natural rather than mechanically replacing every word. The goal is that when the new tasks feature ships, users can tell the difference between `edge tasks` inside a guide and `tasks` they manage.
5. Phase 0: Update docs, invariants, and tests to reflect the renamed guide concept.
   Update `AGENTS.md`, relevant feature docs, and tests that currently talk about guide tasks so they use the new `edge task` terminology. In particular, repo invariants like ordering by `order` then `id`, seed comments, and schema explanations should stop using bare `tasks` when they mean the guide feature.
6. Phase 1: Start the new user-managed tasks feature only after the rename is complete.
   With the guide feature now renamed, add a new tasks domain that mirrors the rewards feature’s navigation and scope split, but awards reward credits on completion instead of spending them. Use explicit names throughout (`selfTasks`, `partnershipTasks`, `selfTaskCompletions`, `partnershipTaskCompletions`) and reserve plain `task` for this new feature from this point onward. Scope for v1 is: self tasks on `/home/tasks`; partnership tasks on `/partner/[id]/tasks`; one-off and repeatable tasks; reward-credit grants on completion; random completion messages; completion history; no per-occurrence editing or exception dates.
7. Phase 1: Define the new task-domain rules in a pure module before wiring routes.
   Add a pure task-domain helper parallel to the rewards domain to encode permissions and completion eligibility. The rules agreed in planning are: self tasks are fully self-managed; in a partnership with one-sided control, the controlling side can create and edit but cannot mark done, while the non-controlling side can mark done but cannot create or edit; under shared control both can create and both can mark done, but nobody can complete a task they personally created; completing a task awards credits to the person who completed it; missed fixed-schedule recurrences roll forward with no backlog.
8. Phase 1: Add the timezone ownership model for task dates before implementing recurrence.
   Any task field that represents a date or datetime must carry a companion flag indicating which user the value is relative to. For self tasks, that owner is always the account holder, so no extra UI is shown. For partnership tasks, store a stable user reference on the task field itself, using the relevant user id rather than a raw timezone string, so the meaning survives later timezone changes and does not depend on who is viewing the task. The stored datetime remains UTC, but it is interpreted as having been entered in the associated user’s local timezone at the time of editing, and future displays stay relative to that user’s current account timezone.
9. Phase 1: Model recurrence as one structured spec with timezone-aware date ownership.
   Use one JSON schedule spec on each new task row plus a small set of scalar summary fields. The supported modes should be: `oneOff`, `rollingWindow`, `afterCompletion`, and `scheduled`. Any schedule mode that contains a date or datetime anchor must also store which user owns that anchor timezone. The `scheduled` form should expose only the major patterns users expect: every `N` days, every `N` weeks on selected weekdays, every `N` months either on day-of-month or nth weekday, every `N` years, optional start datetime, optional end (`never`, `on date`, `after count`), and a `weekdays` preset. Do not expose raw RRULE text, custom exclusions, holiday calendars, mixed-times-in-one-rule, or per-occurrence overrides in v1.
10. Phase 1: Choose the storage model for the new tasks feature that keeps reads cheap and history truthful.
   Extend the app schema with separate self-task and partnership-task live tables plus completion-history tables. Each live task should store: ids, owner or partnership scope, `createdByUserId` for partnership tasks, title, description, `active`, `creditsAwarded`, `completionMessages` as a JSON array of strings, the structured schedule spec, any task-level or field-level timezone-owner references required by the chosen form design, `lastCompletedAt`, `completedCount`, and `nextEligibleAt` or `nextDueAt` summary state so list pages do not have to replay full history to decide whether a task is completable. Each completion row should snapshot: task id, title, description, credits awarded, the random message actually shown, who completed it, who created it for partnership rows, and the completion timestamp. Keep `creditsAwarded` on the task as a non-negative integer where `0` means `no credits`.
11. Phase 1: Reuse existing reward-credit tables rather than inventing task-credit tables.
   Self-task completion should increment the user’s existing self reward-credit balance in `self_reward_credits`. Partnership-task completion should increment the completer’s existing partnership reward-credit balance in `partnership_reward_credits`. Completion actions must write the completion row and the credit increment in the same `db.batch()` so balance and history cannot drift.
12. Phase 1: Extend the timezone utility layer before building the task UI.
   The current timezone utilities only validate canonical IANA names and detect the device timezone. Add helper functions that can: read the viewer timezone and a partner timezone from existing account data; convert a local date or datetime entered for one user into the stored UTC value; format a human-readable timezone label for a given user timezone; and calculate the offset difference between the associated timezone and the viewer’s current timezone at the specific displayed instant, not relative to UTC alone. The offset helper must be DST-aware so a note like `(+/- XXh YYm from your time)` is correct for the actual date being viewed.
13. Phase 2: Add validation schemas and typed view models.
   Add Zod schemas for task create/edit, completion, and any credit/message subfields in the existing `src/lib/schemas` pattern. The task form schema should validate `title`, `description`, `active`, `creditsAwarded`, `completionMessages`, schedule-spec fields for the selected mode, and the timezone-owner selector for every applicable date/datetime field. Also add new shared view types in `src/lib/types.ts` for task rows, completion history rows, self-task sections, home partner-task sections, and capability flags such as `canManage`, `canComplete`, `createdByMe`, `nextEligibleAt`, a pre-rendered `scheduleSummary` string, and optional timezone-note view data for each rendered date/datetime.
14. Phase 2: Build server-side task services by mirroring the rewards structure and threading timezone metadata through every view.
   Add a new server task service parallel to `src/lib/server/rewards.ts`. It should expose: self-task page loaders; partnership membership gating built on `getPartnershipForUser()`; create/update/toggle operations; completion operations that increment credits and append history in one batch; history readers; and home aggregation for partner-task sections. Every query should select only the needed columns. Every action should re-check permission server-side rather than trusting the form. Partnership completion must enforce both the current control rule and the author-not-completer rule. Every read model that includes a task date or datetime must also include enough timezone-note metadata to decide whether the viewer should see the de-emphasized note and what text it should show.
15. Phase 3: Extend route loads so partner pages know both timezones where needed.
   The root layout already exposes the signed-in user timezone. Extend the relevant partner-facing loads or shared partner service views so task routes can also read the counterpart user’s timezone without creating a second ad hoc partner lookup path. Use that data both to decide whether to show the timezone-owner toggle in the form and to render timezone notes on task views. If both users currently share the same timezone, omit the extra UI entirely.
16. Phase 3: Add the new routes and keep the navigation parallel to rewards.
   Add a home tasks hub under `/home/tasks` that mirrors the current rewards hub shape: a self-tasks section plus one claim-style section per partner. Add nested self-task routes for add, edit, and history if needed to match the current rewards flow. Add a partner tasks route under `/partner/[id]/tasks` plus nested add, edit, and history routes. Update the signed-in home page quick links to add a Tasks button next to Guides and Rewards. Update the partner page actions to add a Tasks button next to Messages and Rewards.
17. Phase 3: Keep the home tasks hub focused like the home rewards hub.
   The home tasks hub should show one self-managed section and then one section per partner. The self section owns self-task creation, editing, activation, completion, and history. The partner sections should be completion-focused summaries, like home rewards already is for partner rewards, not a second management UI. Editing and creating partnership tasks should stay on `/partner/[id]/tasks`.
18. Phase 3: Design the task form UI around timezone-relative entry with minimal extra controls.
   The repeat controls should use progressive disclosure: first choose `One-off` or `Repeatable`; then, if repeatable, choose `Anytime`, `After completion`, or `On a schedule`; then show only the controls for that mode. For any partner-task date or datetime field, default the timezone owner to the other partner on create. If the viewer and partner have different timezones, show a small toggle next to the relevant field that switches between `your time` and `their time`, with text that also communicates the partner’s current offset difference from the viewer. If the two timezones are the same, suppress this UI entirely. Self-task forms never show this toggle.
19. Phase 3: Extract the existing partner-page timezone display into a reusable component, then use its format for task timezone notes.
   The partner page already has the target rendering language: humanized timezone plus the relative offset wording, currently shown as `current time + timezone name + offset`. Break that out into a dedicated component or tightly related pair of components so the partner page and task surfaces share one implementation. Task dates and datetimes associated with a different timezone than the viewer’s current timezone should render the same format as the partner page except without the leading current time, still with the globe icon, humanized timezone name, and viewer-relative offset wording. This reusable component should own the display rules so task detail and task-list contexts do not rebuild the string ad hoc.
20. Phase 3: Define explicit v1 exclusions so complexity does not leak in later.
   Exclude from v1: arbitrary RRULE editing, exclusion dates, multiple different times in a single rule, holiday-aware schedules, workday/business-day calendars, per-occurrence rescheduling, backfilling missed occurrences, multiple future generated instances, and background auto-completion or auto-crediting. The task exists as one live row with one next-eligible state; completion advances it.
21. Phase 4: Add full test coverage at the same layers rewards uses.
   Add pure tests for task-domain permissions and eligibility calculations, including timezone-owner conversion and offset-note formatting around DST boundaries. Add server tests for membership gating, self-task completion credit increments, partnership control matrices, shared-control creator restrictions, inactive-task visibility, missed-schedule roll-forward behavior, rolling-window limits, delayed-repeat unlocks, and completion-history snapshots. Add route tests for `/home/tasks` and `/partner/[id]/tasks` loads and actions, including the cases where partner and viewer timezones match and differ. Add Playwright coverage for create/edit/complete flows across self tasks and partner tasks, verifying the toggle only appears when appropriate, defaults to partner time on create, stored dates survive later account timezone changes, credits actually change in the existing rewards UI after completion, and the displayed completion message is one of the configured messages. Also add focused regression coverage for the `edge task` rename where queries, seeds, and guide ordering now point at `edge_tasks`.
22. Phase 4: Update documentation, including timezone and README changes, as part of the same change.
   Add a dedicated feature doc describing the new task data model, recurrence modes, control rules, credit-award behavior, timezone-owner semantics, UTC storage versus user-relative interpretation, and the route split between `/home/tasks` and `/partner/[id]/tasks`. Update `docs/timezone.md` so it no longer describes timezone as only an account-level preference, but also explains how task dates can be associated with one partner or the other and why a user-id-relative model survives later timezone edits. Update `README.md` by adding a concise Features section and a note that partner tasks support differing timezones, including relative rendering when a task date belongs to the other partner’s timezone. Update AGENTS documentation with the renamed `edge task` terminology where it currently refers to the old guide task model, and copy this exact approved plan into `docs/historical-plans/YYYY-MM-DD-*.md` once the implementation is finished, per repo convention.
23. Phase 5: Verify narrowly first, then run the full repo loop.
   Validate the `edge task` rename and migration first with focused tests around guide loading and seeding. Then validate the timezone utility additions and timezone-note formatting with focused unit tests before new task routes depend on them. Then validate the recurrence utility, task service tests, task route tests, and the new Playwright flows. Finish with the repo’s required end-to-end verification loop: `npm run check`, `npm run lint`, `npm test`, and `npm run test:e2e`.

**Decisions**
- The existing guide `tasks` concept is renamed to `edge task` before the new tasks feature is added.
- The database rename is done with a new forward migration, not by rewriting committed migration history.
- Route IA for guides stays under `/home/guides`; the rename is primarily to disambiguate the concept and database/model names.
- Self tasks are included and fully self-managed on `/home/tasks`.
- Completing a task awards credits to the person who marked it done.
- Missed fixed-schedule recurrences roll forward with no backlog.
- For partner tasks, timezone ownership is stored as an explicit user reference, not as a timezone string and not as a viewer-relative label.
- Self tasks always use the owner’s own timezone and show no timezone toggle.
- Partner-task date/datetime inputs default to the other partner’s timezone on create.
- If both partners currently share the same timezone, the toggle UI is suppressed.
- Any displayed task date/datetime whose associated timezone differs from the viewer’s current timezone shows a de-emphasized timezone note using the same format as the partner page’s timezone line, except without the current-time prefix, and that formatting is owned by a reusable component shared with the partner page.
- v1 supports date+time recurrence, but stored datetimes remain UTC and are interpreted through timezone-owner metadata rather than hard-coding a timezone name on the task field.
- Partnership tasks deliberately diverge from rewards under one-sided control: the controller manages tasks, the other side completes them.
- Under shared control, both sides can create and both can complete, but nobody can complete a task they created.
- Reuse existing reward-credit balances instead of creating separate task-credit balances.
- Use RRULE internally only for the fixed-schedule mode; keep the user-facing controls structured and constrained.

**Further Considerations**
1. Decide whether task timezone ownership should be stored per field or once per task if v1 only ever has one date/datetime anchor; per-field storage is more future-proof, but task-level storage is simpler.
2. Decide whether the guide UI should consistently say `edge task` anywhere a guide step is rendered, or whether some screens should use a softer user-facing term like `step` while the database/types still use `edge task` internally.
3. If you want `edge task` to replace the old term in guide seed prose verbatim, treat that as a content migration decision, not just a code rename, because the seed data is deliberately human-authored copy.
