# Partners

_Implemented 2026-09-07. A frozen record of what was intended at that moment —
do not cite it as current behaviour, and do not update it as the code moves on._

## Why

The bottom nav already rendered a tab per "partner", fed by a hard-coded list in
`src/lib/placeholder-partners.ts`. There was no `partnerships` table and no way
for one account to link with another. This adds the real feature: an invite you
send out-of-band, a confirmation the other person accepts, and a permission
setting that decides which of the two may change the link afterwards.

## What was decided

**One row per link, not one per direction.** The two names and the single
control setting are properties of the relationship; storing them twice would let
the two halves disagree. `inviter_id` / `invitee_id` keep their meaning after
acceptance, and `control` is stored against those permanent roles
(`'inviter' | 'invitee' | 'both'`) so a row reads the same from either end.
Everything per-viewer is derived at read time by `viewPartnership()`.

**The question is asked from the asker's side, the answer is stored from the
link's side.** "Who's in control?" is answered `me` / `them` / `mix`;
`controlFromAnswer()` and `answerFromControl()` are the only translation.

**Control gates editing, never leaving.** A user who handed control to their
partner must still be able to disconnect, so `deletePartnership` checks
membership only. Confirmed with the user before building.

**The invite token is stored in the clear**, with a seven-day expiry, and can be
rotated. Hashing it would mean the inviter could never be shown the link again,
and re-sending an already-created link was a requirement. Better Auth stores
`session.token` the same way, so this grants an attacker with database read
access nothing they would not already have. Cleared on accept.

**Extra questions:** one optional shared label for the connection
("partner", "trainer"). The user chose this over a private note or a
progress-visibility toggle.

## Things found along the way

Three bugs that predate this work or were caused by it, all caught by the new
tests and all now carrying a comment at the site:

- **`disabled={x || undefined}` on a `wa-*` element leaves it permanently
  disabled.** Web Awesome's alpha coerces the property to true. The existing
  "Add a passkey" button was unclickable. Now `disabled={x}` everywhere.
- **`InputField` never rendered a value.** Invisible for login and signup, whose
  fields start empty, but every prefilled form came up blank and posted the
  blanks back. It now renders from and writes back to the superforms proxy.
- **The invite page's "Log in" / "Sign up" buttons duplicated the header's link
  names.** Renamed to "Log in to accept" / "Create an account".

## Deliberately not done

- No decline action — the accept screen offers "Not now", which just leaves.
- No notification to the inviter when an invite is accepted.
- `/partner/[id]` still has no shared content; it names the link and points at
  its settings.
- Permissions cover the names, the label and the control setting. They do not
  yet gate anything about guides or progress.
